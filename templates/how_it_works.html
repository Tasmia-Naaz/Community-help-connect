How Community Help Connect Works

A step-by-step walkthrough of our role-based workflows, transparent matching algorithm, and privacy safeguards.

For Help Seekers
  1. Submit Request: Select one of the 6 categories, describe your need, specify urgency level (Normal, Urgent, or Critical), and enter your locality.
  2. Choose Privacy Level: Keep your contact details hidden, visible only to the accepted volunteer, or public.
  3. Track Progress: Monitor real-time status transitions: Pending → Accepted → In Progress → Completed.
  4. Manage Tasks: Cancel a request if assistance is no longer needed before or during progress.
Register as Help Seeker
For Volunteers
  1. Smart Matching: The system automatically prioritizes nearby tasks and urgent/critical needs in your locality.
  2. Accept Open Tasks: Concurrency-safe atomic database transactions ensure only one volunteer can accept each task.
  3. Direct Coordination: Access the seeker's contact info (if authorized) to coordinate pickup, delivery, or transit.
  4. Update Lifecycle: Move the task to "In Progress" and finally "Completed" once the task is finished.
Register as Volunteer
For Resource Donors
  1. Report Surplus: List available supplies, meals, wheelchairs, or blankets with quantity and pickup instructions.
  2. Perishable Safeguards: Enter best-before expiry dates for food. Expired items are automatically withdrawn.
  3. Coordinate Collection: Verified volunteers can reserve and collect items for community distribution.
  4. Listing Control: Easily withdraw, pause, or update listings from your personal donor dashboard.

Under the Hood: Technical Architecture (Viva Highlights)

Rule-Based Matching Algorithm

Rather than relying on unexplainable machine learning or costly third-party map APIs, matching is powered by deterministic heuristics: Locality Match (+40 pts), Active Emergency Zone (+60 pts), Urgency Level (Critical: +100, Urgent: +50, Normal: +10), and Request Age (+1 pt per 2 hours).

Atomic Duplicate Acceptance Prevention

To prevent race conditions where two volunteers click "Accept" simultaneously, the backend utilizes SQL row-level locking (with_for_update()) inside an isolated database transaction. If another volunteer has already accepted, the transaction rolls back cleanly.

Comprehensive Status History Audit Log

Every transition (Created, Accepted, In Progress, Completed, Cancelled, Withdrawn) generates an immutable record in the status_history table with previous status, new status, timestamp, and the actor's user ID.

Role-Based Access Control (RBAC)

All routes enforce role verification on the server with custom Python decorators (@login_required, @role_required, @admin_required). URL manipulation and cross-user tampering are strictly prevented.
